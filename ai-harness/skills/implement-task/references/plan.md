# Plan

Make a plan that remains usable after a break without prescribing the entire
solution.

State the goal, approach, acceptance criteria, constraints, and relevant
trade-offs. Map proposed files to responsibilities using the patterns found
in research. Split larger tasks into ordered slices with an observable result,
dependencies, and a check for each. Include failure cases that affect the task.

For a small change, a short plan in the workspace is enough. Use a linked
`plan.md` beside it when the plan is large. Do not require code listings,
2–5 minute steps, artificial commits, or extra tests for configuration changes.

Check coverage of acceptance criteria and consistency of contracts between
slices. Identify assumptions explicitly instead of writing vague “appropriate
error handling” steps. Record decisions and proposed verification, not invented
results. At plan-review involvement, show the concrete plan and wait for the
requested review. At autonomous involvement, proceed with the authorized scope.
